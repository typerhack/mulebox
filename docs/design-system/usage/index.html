What each job really used

Mockups of 2026-11-25 for M23.8, to pick from before anything is built. Every agent job and every GitHub run now keeps its peak cores (the busiest 10 s), its peak memory, the stage of each and its average. Two questions: where the summary per project and job lives and how it reads against the node's size, and how one run shows its usage on its page.

A

A Usage page of ranges

Fable suggests for the summary

Its own entry in the header; a row per job, each measure a bar whose whole length is the node, with the usual peak, the highest and the size that fits.

  • Summary a page beside Statistics, grouped by node.
  • Heavy is a long bar; the numbers under it.
  • One run a Usage panel under Stages, two bars against the node.
 B

A map in Statistics

Fable suggests for one run

A second part of Statistics; a node as a frame, cores across and memory up, every job a point in it, with the list beside it.

  • Summary a section of Statistics, one node at a time.
  • Heavy is up and to the right.
  • One run no new panel: each peak written under its stage.
 C

Boxes on the Machines page

Under each node, its jobs in the boxes slots use, one per core, and how many of each job would fit side by side.

  • Summary a panel per node on Machines.
  • Heavy is "1 at a time".
  • One run a sentence and rows in Job details.

The summary: A. The owner's question is "what does each job need, on this node", once per job, and a row with two bars on the node's own scale answers it without anything to learn; its figures are the ones mulebox usage prints, it stays readable at 390 px and at a hundred jobs, and it shows spread, which decides whether a size should follow the usual run or the worst one. B's map is the better picture of "big in both" but shows one node at a time and crowds; it could join A's page later, above the rows. C does the sum of job sizes before job sizes exist, and "2 at a time" on a page that acts on nothing would mislead.

One run: B. What a single run adds to the summary is where its peaks happened, and the stages are already drawn: two lines under them say it with no new panel, on a page that already holds Stages, Tests, the log and the details. A's panel is clearer against the node and is the fallback if words prove too quiet; C's sentence is the least to build and the easiest to miss.

Every option shows the same twelve jobs on three nodes: build-1 (Linux, 8 cores, 16.0 GB), mac-1 (macOS, 10 cores, 32.0 GB) and build-2, whose older worker sends no usage. Agent jobs and GitHub runs are mixed; one job is too short to measure cores. Each page has the summary, the summary at 390 px, a finished job's page, and the same part for a running job, a running GitHub run and the two gaps. The rest of the dashboard is as today. Static pages with example data; colours, type, space and corners come from tokens.css; the icons are Lucide, outline.
